CUDA 通俗入门：从 for 循环到 GPU 线程

东京大学《并行与分布式编程》CUDA 一讲的学习笔记。用"阅卷中心"的比喻，配上图解和一个小计算器，把线程、block、shared memory、同步和 block 大小的选择讲清楚。

🏫 前言：把 GPU 想成一个"阅卷中心"

这是我学东京大学田浦健次朗老师《Parallel and Distributed Programming》课程中 CUDA 一讲（讲义 PDF）时整理的笔记。讲义默认你学过 OpenMP，我把它改写成了更口语的版本，并配了图。

CPU 是几位资深老师：每个人都很能干，但人数少。

GPU 是一个阅卷中心：成千上万个阅卷员，每个人能力一般，但人多力量大。

kernel 是发给阅卷员的一张操作说明，只写"拿到一份卷子后怎么改"，描述的是一个人做的事。

thread（线程） 是一个阅卷员；block（线程块） 是坐同一张桌子的一组人，桌上有共用的小白板；SM 是一间阅卷室，里面能同时放好几张桌子；warp 是桌上每 32 个人一排，必须动作完全一致，像做广播体操。

整份讲义可以浓缩成一句话：你只需要写好"一个人怎么改一份卷子"，然后请一大群人同时来改；同桌的人可以互相配合，不同桌的人尽量别互相依赖。

⚖ 第一部分：CPU 和 GPU 计算上的区别

同样 10 份任务：CPU 一个核心依次做 10 步；GPU 10 个线程各领一份，同时做。

CPUGPU
核心数几个到几十个成千上万个
单个核心很强：能预测分支、乱序执行，有大缓存很简单，没有这些花哨功能
追求单个任务尽快做完（延迟）单位时间做完的总量最大（吞吐）
适合逻辑复杂、分支多、步骤相互依赖同一操作作用在海量数据上
线程数约等于核数；远超核数通常是坏主意开几十万个线程是常态
CPU 像几位数学教授，能解难题，但一次解不了几道；GPU 像一万个小学生，每人只会做加法，但一万道加法同时交给他们，一眼就做完。

为什么 GPU 上要开那么多线程？

阅卷员经常要等卷子送来（从内存读数据很慢）。管理员的办法是：这一排在等，就立刻让另一排开工，换人几乎不花时间。屋里坐的人越多，越能保证总有人在干活。这就是讲义第 12 页强调的：CUDA 里开十万个线程很正常，在 CPU 上则要把迭代切给与核数相当的线程。

讲义也提醒了：这不等于 GPU 的并行度比 CPU 高三个数量级。CPU 每个核内部也有 SIMD、指令级并行，只是 OpenMP 阶段还没用上，后面的 SIMD 课会讲。
GPU 的 warp（32 个线程一排）必须执行相同的指令。如果同一排里有人走 if、有人走 else，两条路要先后各走一遍，另一半线程空等（warp divergence）。所以分支很多的代码不适合 GPU。

🚀 第二部分：Kernel 的写法与启动

做什么怎么写
声明一个能在 GPU 上跑的入口函数__global__ void f(...) { ... }（必须返回 void）
从 CPU 启动它f<<<nb, bs>>>(...); 产生 nb × bs 个线程
编译nvcc program.cu；想让 .cc 也按 CUDA 编译：nvcc -x cu program.cc

把 for 循环改成 CUDA 的"万能模板"

cuda// 原来的串行写法
for (long i = 0; i < n; i++)
    S(i);

// ① 把"一次迭代"写成 kernel
__global__ void S_fun(long n) {
    long i = blockDim.x * blockIdx.x + threadIdx.x;   // 我是第几号
    if (i < n)                                        // 多出来的线程什么都不做
        S(i);
}

// ② 启动足够多的线程（可以比 n 多）
int  bs = 64;                      // 每个 block 的线程数（先用 64，后面会解释）
long nb = (n + bs - 1) / bs;       // 向上取整，保证 nb * bs >= n
S_fun<<<nb, bs>>>(n);
cudaDeviceSynchronize();           // 等 GPU 做完再往下走

启动是"交代完任务就走"

kernel 启动后 CPU 不等 GPU，继续往下执行；但两个 kernel 之间默认在 GPU 上排队串行。需要结果时必须同步：

cudah0();
g0<<<...>>>();   // 发出去就不等了
h1();            // g0 和 h1、h2 可能同时在跑
g1<<<...>>>();   // g1 要等 g0 做完才开始（默认排队）
h2();
g2<<<...>>>();
cudaDeviceSynchronize();   // 到这里才等 GPU 全部做完
h3();                      // 这时 h3 不与任何东西重叠
常见的三个坑：
  • 没同步就读结果：读到的是旧值；程序若直接退出，kernel 里的 printf 也可能一行都打不出来。
  • 计时陷阱：只在启动前后取时间，量到的是"启动开销"，不是 kernel 执行时间。计时前要先同步。
  • 静默失败：例如把 bs 写成 2048（上限 1024），程序不会崩，只是 kernel 根本没运行。所以每次都要检查错误。
cudaf<<<nb, bs>>>(...);

cudaError_t e1 = cudaGetLastError();        // 启动本身有没有出错（如 bs > 1024）
cudaError_t e2 = cudaDeviceSynchronize();   // kernel 执行过程中有没有出错
if (e1 != cudaSuccess || e2 != cudaSuccess) {
    fprintf(stderr, "%s / %s\n", cudaGetErrorString(e1), cudaGetErrorString(e2));
    exit(1);
}

🔢 第三部分：线程编号

n = 10，每个 block 4 个线程，需要 ⌈10/4⌉ = 3 个 block；多出来的 2 个线程由 if (i < n) 挡住。

内置变量含义图中的值
gridDim.x一共有几个 block3
blockDim.x每个 block 有几个线程4
blockIdx.x我在第几个 block0、1 或 2
threadIdx.x我在 block 里排第几0～3
全局编号：i = blockDim.x * blockIdx.x + threadIdx.x；总线程数：gridDim.x * blockDim.x。它们分别对应 OpenMP 的 omp_get_thread_num() 和 omp_get_num_threads()。
二维、三维编号怎么回事？

处理图片或矩阵时，用二维编号更自然：blockIdx.y、threadIdx.y 就是第二个方向的编号。启动时用 dim3 类型：

cudadim3 nb(10, 10);   // 10×10 个 block
dim3 bs(8, 32);    // 每个 block 8×32 个线程
f<<<nb, bs>>>(...);   // 总线程数 = 10*10*8*32

它只是换了一种编号方式，本质上还是一堆线程，没有新概念。

一个 warp 里的 32 个线程，threadIdx.x 是连续的。所以用二维编号时，让 x 对应数组里连续存储的那一维，32 个线程读相邻地址，内存访问效率最高（coalescing）。

🏷 第四部分：函数前的三个关键字

CPU 和 GPU 是两个独立的设备，所以每个函数要标明"在哪里运行、谁能调用"。

关键字在哪里运行谁能调用比喻
__global__GPUCPU（用 <<<>>> 启动）总指挥下发给阅卷中心的任务单
__device__GPUGPU 上的函数阅卷员自己用的小工具
__host__CPUCPU（不写关键字时默认就是它）你平时用的普通函数
  • __global__ 函数必须返回 void：因为发出去就不等了，没法直接把结果还给你。
  • 给同一个函数同时写 __host__ __device__，编译器会生成 CPU、GPU 两个版本。
  • 两个宏：__NVCC__（用 nvcc 编译时有定义）、__CUDA_ARCH__（编译 GPU 版本时才有定义），可用来在同一份源码里写两套实现。

🏢 第五部分：为什么要分 block？执行模型

软件上的层级和硬件上的执行单元一一对应。

block 分给 SM 的过程，就像阅卷中心排桌子：

  1. 你下发了 1000 张桌子（block）的任务，它们在门口排队。
  2. 哪间阅卷室（SM）有空位，就叫一张桌子进去。
  3. 一张桌子不会拆开，必须整张进同一间屋子。
  4. 一间屋子可以同时放好几张桌子，放得下为止。
  5. 某张桌子做完了，下一张马上补位。
这样设计的好处：不管你的 GPU 有 20 间还是 132 间阅卷室，程序都不用改。代价是不同桌子之间不能互相等待或交换数据（因为不知道谁先谁后进屋）。所以 CUDA 的协作工具都只在同一张桌子内有效：
  • shared memory：桌上的小白板，只有同桌能看到
  • __syncthreads()：同桌喊一声"都停一下，等齐了再继续"
不用这两样时，桌子多大只影响速度，不影响结果对不对。

🗄 第六部分：数据放在哪里，谁能看到

大仓库人人可见；小白板只有同桌可见。

① CPU 和 GPU 之间

以前：CPU 和 GPU 各有各的仓库，要先 cudaMemcpy 把数据搬过去，算完再搬回来。现在（GH200 这类带硬件缓存一致性的新平台，NVIDIA 叫 NVLink-C2C，AMD 叫 Infinity Fabric）：两边像共用一个文件柜，直接拿就行：

cuda__global__ void f(int *p) { *p = 42; }

int main() {
    int a = 0;
    f<<<1, 1>>>(&a);          // 直接把普通变量的地址交给 GPU
    cudaDeviceSynchronize();  // 等 GPU 写完
    printf("a = %d\n", a);    // 直接读结果（在课程使用的 GH200 上成立）
}

全局变量、局部变量、malloc/new/mmap 的内存都可以这样用，只关心正确性的话完全不需要 cudaMalloc。

能直接访问不代表一样快：GPU 读"CPU 那边的内存"会比读自己的显存慢（性能问题讲义留到后面几周）。另外这是课程所用硬件的特性，换到别的机器上不一定成立。旧的 cudaMallocManaged 在没有硬件一致性的时代往往拖慢性能。

② GPU 里所有线程之间

大仓库（global memory，也就是普通内存）里的东西，所有线程都能看到：谁写进去，别人"迟早"能读到。注意是"迟早"，不是"马上"。

③ 同一张桌子的线程之间：shared memory

  • 只有同一个 block 的线程能看到；block 结束后内容就没了。
  • 物理上是 SM 里的片上小存储，速度和缓存相当，比大仓库快得多；容量小（GH200 每个 SM 共 256KB，与 L1 共用，最多约 228KB 可作 shared memory）。
  • 讲义作者吐槽这个名字起得不好：大仓库其实也是"共享"的，白板只能"桌内共享"。
cuda// 启动时指定每个 block 的小白板大小（字节）：第三个参数
f<<<nb, bs, S>>>(...);

// kernel 里使用
__shared__ int a[128];                  // 大小是编译期常量时
extern __shared__ char whatever[];      // 大小在启动时才决定时：拿到起始地址，自己切分
int *p = (int *)whatever;
如果先放 char 再放 double 切分动态 shared memory，后者可能落在没对齐的地址上。经验是把对齐要求大的类型放前面。另外新 GPU 的 L1 缓存越来越聪明，很多以前必须手写 shared memory 的优化现在交给硬件缓存也不差，讲义说它的重要性"在变化"就是这个意思。

💥 第七部分：多个线程同时改同一个数——撞车

黑板上写着 100，A 和 B 同时看到这个 100，A 加 1 写回 101，B 也加 1 写回 101，本该是 102，结果只有 101，少了一次。这就是数据竞争（race condition），大仓库和小白板都会发生，和 CPU 多线程一样。

要做的事OpenMPCUDA
大家往同一个数上加#pragma omp atomicatomicAdd 等
一次只让一个人进去critical / 锁没有对应物
所有人等齐再继续barrier桌内 __syncthreads()；全体用 cooperative groups
求总和reduction只在一个 block 内有；全体要自己用 barrier 搭

atomicAdd：排队加分

atomicAdd(p, x) 的意思是"这一步一气呵成，中间不许别人插手"。结果一定正确，但一万个线程排同一条队，等于又变回一个人干活，所以很慢。

cuda// 有数据竞争（会少加）
__global__ void sum(int *a, int *p, long n) {
    long i = blockDim.x * blockIdx.x + threadIdx.x;
    if (i < n) *p += a[i];
}

// 正确，但所有线程排同一条队，很慢
__global__ void sum(int *a, int *p, long n) {
    long i = blockDim.x * blockIdx.x + threadIdx.x;
    if (i < n) atomicAdd(p, a[i]);
}
讲义第 29–30 页的例子写的是 if (i > 0)，应为 if (i < n)，否则会漏掉 a[0] 并可能越界，应该是笔误。上面代码已更正。
CUDA 没有 critical/锁，是因为 warp 里 32 个线程共享指令指针：如果同一排里有人拿到锁，其他人原地空转等锁，而拿到锁的那个又被绑在这一排里无法往下执行去解锁，容易变成互相等死。所以 CUDA 不鼓励（也不提供）这种做法，改用 atomic 和 barrier。

barrier：所有人等齐再走

桌内一直有 __syncthreads()。现在也支持全体线程的 barrier，靠 cooperative groups：

cuda#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ void k(double *c, long n) {
    cg::grid_group g = cg::this_grid();   // "全体线程"这个组
    unsigned long long i = g.thread_rank();   // 我是第几号
    // ... 做一部分工作 ...
    g.sync();                              // 全体 barrier：所有人到齐才继续
    // ... 再做下一部分 ...
}

// 要用 g.sync()，必须换一种启动方式：
void *args[] = { &c, &n };
cudaLaunchCooperativeKernel((void *)k, nb, bs, args);   // 而不是 k<<<nb,bs>>>(c, n)
讲义说用 cooperative 方式启动"有个后面再讲的注意事项"，但讲义里没有展开。实际是：cooperative 启动要求所有 block 必须同时驻留在 GPU 上。如果 block 太多、装不下，有的在门外排队，而屋里的在等门外的，就会互相等死，所以启动会直接失败。block 数量因此有上限。

🏆 第八部分：用 barrier 搭一个"求总和"（归约）

思路像淘汰赛两两合并：每一轮让后一半的人把值交给前一半对应的人，人数减半；大约 log₂n 轮之后只剩 0 号，他手里就是总和。

每轮之间必须有 barrier：下一轮要读的值，必须是上一轮已经算完的。

要点说明
不变式每一轮结束后，"c[0:m] 的和 = 原数组的总和"，然后让 m 减半
奇数个怎么办取 h = (m+1)/2（向上取整），中间多出来的那个原样留到下一轮。可用 n = 1、2、3、7、10000 检验边界
为什么每轮要同步下一轮线程 i 要读 c[i+h]，它可能是上一轮别的 block 的线程写的，不同步就会读到旧值
最容易犯的死锁g.sync() 必须放在 if 的外面。这一轮没活干的线程也必须去报到，否则其他人会永远等下去
还能更快全体同步很贵，桌内同步便宜得多。讲义提示：可以先在 block 内归约，再把各桌的小计汇总
具体怎么把这几点写成 kernel，是课程作业 Problem 2 的内容，这里只记思路，不放完整实现。

📏 第九部分：一张桌子坐多少人？为什么是 64

总线程数固定（比如 1000 万）时，每个 block 该坐多少人？讲义分三步缩小范围：

  1. 硬限制：block 大小 ≤ 1024。
  2. warp：32 个线程一排，不是 32 的倍数，最后一排有空位也照样占着，浪费。所以只考虑 32、64、96……1024。
  3. 驻留数量：一个 SM 同时能放多少个 block（驻留 block）取决于三样东西，取最小的：硬件上限（如 32）、寄存器、shared memory。
驻留线程数 = B · min(⌊R / (R₀·B)⌋, ⌊S / (S₀·B)⌋, 32)。其中 B 是 block 大小，R、S 是 SM 的寄存器/shared memory 容量，R₀、S₀ 是每个线程的用量。前两项里 B 越小越好，但 B = 32 时 32 × B 太小，填不满 SM。结论：32 太小，64 够用，没有特殊理由就选 64。

🧮 交互计算器：拖动"每线程寄存器数"，看哪种 block 大小塞得最满

模型假设（Hopper SM 的典型值）：每个 SM 有 65536 个寄存器、最多驻留 2048 个线程、最多 32 个 block。这是简化模型，忽略了 shared memory 和寄存器分配粒度，仅用来理解讲义里的取最小值逻辑。★ 为驻留线程最多者（并列时取最小的 B）。

什么情况下该选更大的 block？

当你希望很多线程一定在同一个 SM 上同时运行时：

  • 线程之间大量通信或同步；
  • 要充分利用 shared memory；
  • 想保证同一时刻只有一个 block 在跑（这样知道是哪些线程在跑）。

这些都取决于具体算法。64 只是没有特殊理由时的安全默认值。

编译时加 -Xptxas -v，nvcc 会打印每个线程用了多少寄存器、多少 shared memory；cudaOccupancyMaxPotentialBlockSize() 可以让运行时直接推荐一个 block 大小。

✅ 自测：6 道小题（点开看答案）

1. f<<<3, 4>>>(...) 一共产生多少个线程？线程的编号 i 范围是多少？

3 × 4 = 12 个线程，i 从 0 到 11。

2. n = 1000，每个 block 64 个线程，需要几个 block？多出多少个线程？

⌈1000/64⌉ = 16 个 block，共 1024 个线程，多出 24 个，需要 if (i < n) 让它们什么都不做。

3. 启动 kernel 后马上读结果，会发生什么？怎么避免？

启动是异步的，CPU 不等 GPU，会读到旧值。需要先 cudaDeviceSynchronize()，并检查返回的错误码。

4. 为什么 g.sync() 不能写在 if (i + h < m) 里面？

barrier 要求所有线程到达。如果没活的线程跳过了它，到达的线程会永远等不齐，程序卡死。

5. atomicAdd 正确但为什么慢？

所有线程对同一个地址做原子加，在那个地址上只能一个一个串行完成，并行度基本丢失。更好的办法是先局部汇总、再全局汇总。

6. 没有特殊理由时 block 大小选多少？为什么不选 32 也不选 1024？

选 64。32 会被"每个 SM 最多驻留 32 个 block"限制住，线程数填不满 SM；块太大时，寄存器/shared memory 用量成倍增加，向下取整浪费多，可驻留的 block 数少。

warp divergence同一 warp 的线程走不同分支，导致两条路依次执行
global memory所有线程可见的普通内存（大仓库）
shared memory只在一个 block 内可见的片上快速存储（小白板）
race condition多个线程同时读写同一位置导致结果错误
atomic不可被打断的读-改-写操作，如 atomicAdd
barrier所有线程到齐才继续的同步点
cooperative groups支持全体线程 barrier 的 API，需用 cudaLaunchCooperativeKernel 启动
resident block当前真正驻留在 SM 上运行的 block
